### Required fixes

1. **One way to compare: `Item::changed` uses the predicate form.** `host_view.rs:258` and `:267` write `request.eq(id).then_some(resolution)` and `call.eq(id).then_some(outcome)`. That is `==` spelled as a method so the checker can't see it, and `examples.md` §22 names this exact spelling (`State::Closed.eq(s)`) as not the form. The same diff writes the same test as `Some(hello).filter(|hello| hello.token == self.token)` in `serve.rs`, so one equality has two spellings in one change. Write `Some(resolution).filter(|_| &request == id)` and `Some(outcome).filter(|_| &call == id).copied()`. +10 tokens, +10.0 score. Proposal 0040 offers the shorter form.
2. **`AuthToken` derives serde; its hex impls go.** `proto/src/ticket.rs:71-81` serialises the token as 32 hex digits through a hand-written `Serialize` and `Deserialize`, which existed so the JSON frame was readable. Postcard isn't readable, so the token now crosses the wire as a 33-byte string where 16 raw bytes would do. Derive `Serialize, Deserialize` on `AuthToken([u8; 16])` and delete the two trait impls, `to_text`, `parse`, `TicketError::Token`, the `HEXLOWER` import and the hex round-trip test (the `Debug` assertion stays). The `Hello` frame test changes to 16 `\xab` bytes. -265 tokens, -262.5 score, and two tolerated trait impls fewer.
3. **The feed's dedupe is unreachable; delete it.** `LogActor::on` builds the replay and calls `live.subscribe()` in one actor turn, and a `broadcast::Receiver` from `subscribe` "will receive values sent after this call" (tokio docs). So no live event can carry a seq the replay already holds, and `Feed::write`'s `match event.seq.cmp(&self.last)` never takes its skip arm. Delete `Feed::last`, `Feed::write` and the `Ordering` and `HostSeq` imports, write `Upcoming::Event(event) => self.send.write(&event).await?`, and say on `Feed` why the two neither overlap nor leave a gap. The reconnect e2e still asserts contiguous seqs with no duplicates. -95 tokens, -87.0 score.
4. **The boundary table sends with `join_all`.** `e2e.rs:232-241` unzips the cases with a four-type turbofish (U4), then sends them in order through `stream::iter(..).then(..)` (U3). The four commands are independent, so `n0_future::join_all(cases.iter().map(|case| link.send(case.body.clone())))` sends them, keeps their order in the result, and the assertion maps `cases` to their `result`. -14 tokens, -6.5 score. It removes U4 and one of U3's two sites.
5. **`Serving` goes; `announce` takes what it prints.** `daemon/src/main.rs:60-65` defines a struct only to carry four values from `host` to `announce`. `host` builds the ticket, spawns the router, calls `announce(&data_dir, &web_url, &ticket)` and returns the `Router`. The printing order is unchanged: the router accepts before the ticket is printed. -19 tokens, -11.0 score.
6. **The ALPN rule says what "breaking" means under postcard.** `proto/src/lib.rs:12-13` says "any breaking change to these types bumps ALPN", and `ALPN`'s doc says the types "change incompatibly". Under postcard almost every change breaks: a variant is its index and a field is its position, so reordering variants or fields decodes as the wrong value with no error, and appending a variant makes an old peer fail mid-stream, the failure the bump exists to prevent. A Home Screen web app keeps running its cached build against a newer host, so this case is real. Write the rule out: any change to a type reachable from `Open`, `HelloReply`, `CommandResult`, `Event` or `Signal`, including adding a variant at the end, bumps `ALPN`; renaming a variant or field does not change the bytes. Comments score nothing.

## The protocol, against units 4 to 7

The `proto` types are §1 verbatim, minus the serde attributes. Read against unit 2's event shapes (`p1-u2-agents`, `crates/agents/src/{claude,codex}/protocol.rs` and `claude/PROTOCOL.md`), they carry what units 4 to 7 need. No gap requires a change in this unit. Four items need a decision or a line in the design before unit 4.

1. **Hold an interrupt until the turn starts (unit 4, session actor).** `PROTOCOL.md` records that an interrupt reaching Claude before `system/init` was ignored in ten of eleven runs, and Codex can't interrupt without the `TurnId` from `turn/started`. The protocol needs nothing for this: the client offers Interrupt while `Running`, and `Accepted` stays the honest answer. The design's `Turn` has only `Idle` and `Running(NativeTurn)`, so §2.5 needs a third state, `Starting { interrupt: Held | NotHeld }`, entered on `Send` and left on `TurnStarted`, which sends a held interrupt then. The command table gets the row "`Interrupt` while `Starting`: hold it, `Accepted`".
2. **`RequestOpened` repeats `ToolCall`'s job in a weaker shape (owner's call, before unit 4).** `ToolCall` carries a typed `ToolKind`, and `RequestOpened` carries `tool: String, detail: String`. Both describe the same tool action, often the same call: Claude prints the `tool_use` block and then `can_use_tool` for it (`fixtures/e2e/claude-approve.jsonl`). `RequestOpened { request, tool: ToolKind }` would let one mapping function and one renderer serve both: Claude's `(tool_name, ToolDetail)` goes through the same `tool_kind` as `ToolUse`, Codex's `Command { command }` is `ToolKind::Command`, and its `FileChange { reason }` and `Permissions { reason }` are `Other` with that reason. This changes §1.4 as approved, which is why it's a question and not a fix. Deciding it now costs nothing; after unit 4 it costs an ALPN bump.
3. **A denied Claude tool shows as `Failed`, not `Declined` (unit 4).** A deny comes back as a `tool_result` with `is_error: true` (`PROTOCOL.md`, step 2), so the mapping gives `Finished(Failed)`. Telling them apart needs the `tool_use_id` that `can_use_tool` carries, which unit 2's `PermissionRequested` doesn't expose. Either unit 4 adds it at the agents boundary, or `Declined` stays Codex-only and the design says so.
4. **A failed send must end the turn (unit 4).** The fold sets `Running` on `UserMessage`. If `send_user` or `send_turn` fails after the actor logged `UserMessage`, the session must log `TurnCompleted { Failed }`, or every client shows it running forever.

Checked and fine: deltas then the final message are adjacent in both providers (Claude prints the `assistant` block before `content_block_stop`; Codex's `item/completed` follows the item's deltas), so the reply rule never shows text twice. An interrupt mid-stream prints the cut-off text as the final message, which replaces the deltas. `SendMessage` during `Starting` waits in the session's inbox, which §2.5 starts reading only after the agent is up. Codex's `Failed { message: Option<String> }` maps to an empty string.

## Postcard

- **Stable.** The frame body is `postcard::to_allocvec` and `from_bytes`, postcard 1.1.3 with `use-std`. Postcard's wire format is frozen for 1.x. Every `proto` type is a struct, a newtype or an externally tagged enum, which postcard encodes; nothing uses `deserialize_any`, `flatten`, `untagged` or `skip_serializing_if`.
- **Deterministic.** No `HashMap` or other unordered collection crosses the wire, so one value has one encoding. That will matter when `redb` stores the same bytes.
- **The literal-bytes tests are honest.** I decoded each expectation by hand against the declaration order: `SendMessage` is `Open` 2, `CommandBody` 1, session 2, `"hi"`; `RequestResolved` is `EventKind` 8 (`SessionCreated` 0 to `RequestResolved` 8), then `Decided` 0, `Approve` 0, `"phone"`; `TurnCompleted` is 9 with `Failed` 2; `ProviderUnavailable` is `Rejected` 2, variant 1. The bytes are literals, not computed, so a reordered enum fails them. They pin about 15 of the roughly 50 variant indices.
- **The wasm build works.** WASM_RESULT
- **The bump policy is written down** in `proto/src/lib.rs`, `ALPN`'s doc and design §10, but not precisely enough (fix 6).
- **Size.** The commit reports an assistant delta shrinking from 82 to 19 bytes. Fix 2 takes 17 more bytes off every `Hello`.

## Gap-free replay and the log actor

- **Order.** `LogMsg::Subscribe` snapshots the events after the cursor and subscribes to the broadcast in one call of `LogActor::on`, so the live receiver starts exactly where the replay ends. `Feed::next` drains the replay before it reads live. Nothing falls between and nothing repeats, which is why fix 3 can delete the dedupe.
- **Epoch.** A `Subscribe` from another epoch closes the stream. The client already resets on the `Welcome` it gets at `Hello` (`a_cursor_from_another_epoch_starts_over_from_the_beginning`), so this branch only guards a client that ignored its `Welcome`.
- **A slow subscriber.** `Log::append` never waits on a subscriber: `broadcast::send` drops the oldest value for a lagging receiver. Each feed has a buffer of `LIVE_BUFFER` (1,024) events. A feed that falls further behind gets `Lagged`, finishes the stream, and the client resubscribes from its cursor. A slow QUIC or data-channel write blocks only that feed's task. This converges as long as the client takes a replay plus 1,024 events faster than the host appends them. The log itself grows without bound, as §8's decision 3 accepts for slice 1.

## Friction points

- **U1, equality outside a predicate, four sites.** The two `host_view.rs` sites are a breach (fix 1). After it, all four use the predicate form, which is the v5 way. Proposal 0040 measures a guard on all four.
- **U2, a loop that ends with nothing to return, three sites.** Not proposed. The same-kind sites are two (`serve.rs` `channels` and `app` `follow`); `events_through` needs `break events` either way. Allowing a bare `break` takes `follow` and `run_link` from 288.5 to 268.0 (-7.1%) and 302 to 280 tokens, under 15%. It is worth watching: `follow` returns `Err(SendError::Stopped)` for a link that ended normally, an error value invented to satisfy the loop rule, which bends quality 4.
- **U3, sequential awaits over a list, two sites.** One site goes with fix 4. The other (`append`, in a test) remains, one site. Not proposed.
- **U4, `_` in a turbofish.** Removed by fix 4.
- **U5, no `*` on a `Copy` value.** `Iterator::copied()` is the v5 form: `.filter_map(..).copied().collect::<Vec<Epoch>>()`. Not proposed. One site.
- **U6, fixed-size random values.** Already ruled: `bootstrap-review.md` §A11 rewrote `random<const N: usize>()` as `getrandom::fill` on a local array. One fn per size follows that ruling. Not proposed again.
- **U7, a one-platform constant.** Accepted. 0016 exempts a module that exists on one platform, and the `storage` module reads well.
- **U8, clap flags in a subcommand.** Accepted. `HostArgs` with `ArgAction::SetFalse` keeps `!` out of `main`.
- **U9, popping the last item.** Accepted. Changing the last item needs it owned, which `pop` gives. `last_mut` needs `&mut` on a value that isn't loop state (0008), and a slice pattern (`pat.slice`) would only replace the inspection, not the `pop`. No construct shortens it without weakening forward data flow.

## Tool notes

- **Comparison methods.** The checker accepts `request.eq(id)` outside a predicate, which is how fix 1's breach got through. 0038 (on `subset-v6`) already bans calling a fallible operator trait's methods by name. The same list should take `PartialEq::eq` and `ne`, and `PartialOrd::lt`, `le`, `gt`, `ge` and `partial_cmp`, so a comparison is an operator inside a predicate or an `Ordering` from `cmp`, and nothing else.
- **Scoring a proposed rule.** `subset score` can't price a construct whose rule the checker doesn't know yet, so 0040's after score is corrected by hand (24.0 off). A `--allow <id>=<tier>` flag that also lifts the matching placement rule would make such proposals reproducible without arithmetic.
