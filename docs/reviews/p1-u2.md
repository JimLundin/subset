This is the reviewer's pass over `9ecea15` (`git diff 7ea697b...rv-p1-u2`), which is unit 2 plus the drift-check change and its review fixes. The contract is `docs/p1/design.md` §2.7, §4.1, §5 (unit 2's row), §9 and §10, under subset version 5. The verdict is **accept, with four required fixes and two required design changes**. Two fixes cut volume (−165.0 score, −176 tokens). One makes `s2` step 1 deterministic, measured live. One corrects the protocol record. The design needs the interrupt rule below in §2.5, and §2.7's two const tables become matches. No proposals.

### Required fixes

   ```rust
   pub(crate) fn tool_detail(tool: &str, input: &Value) -> ToolDetail {
       let shown = match tool {
           "Bash" => field(input, "command").map(ToolDetail::Command),
           "Edit" | "Write" | "MultiEdit" | "Read" => field(input, "file_path").map(ToolDetail::Path),
           "Grep" | "Glob" => field(input, "pattern").map(ToolDetail::Text),
           "WebFetch" => field(input, "url").map(ToolDetail::Text),
           _ => None,
       };
       shown.unwrap_or_else(|| ToolDetail::Text(input.to_string()))
   }

   fn field(input: &Value, name: &str) -> Option<String> {
       input.get(name).and_then(Value::as_str).map(str::to_owned)
   }
   ```

## The flaky `s2` step 1

**The cause.** In `s2-run5.log` the model never asked. Its messages were "I'll create `a.txt` with the exact requested contents" and then "I couldn't create `a.txt`: the current directory is read-only" (`s2-rec5/server1.jsonl`). Under `on-request`, the model decides whether to ask for escalation, so with a `read-only` sandbox it may decide not to try at all. Step 2 failed the same way ("the current directory is read-only"). Step 5 asks which file was created, so it failed with no `a.txt`. Step 6 re-answers step 1's ids, and there were none.

**The deterministic form.** Use `ApprovalPolicy::Untrusted` with `Sandbox::WorkspaceWrite`. Under `untrusted`, Codex itself asks before every command, even `pwd` (`codex/PROTOCOL.md`, and probe run 6 below). It does not depend on the model's judgement of the sandbox. With `workspace-write`, the model sees a writable directory and has no reason to give up. The only model dependency left is that the model runs some command when told to create a file. The old policy also depended on that, and also on the model choosing to escalate.

**Measured live.** I built `s2` with only that change (`s2-after.rs`) and ran it as below. The probe is the same file cut after step 2, so it could run more often (`/tmp/rv-u2-probe/`).

| Run | Policy | Steps 1 and 2 | Full `s2` |
|---|---|---|---|
| Probe, 10 runs (steps 1 and 2 only) | `untrusted` + `workspace-write` | 10 of 10 PASS | |
| Full `s2`, 5 runs (`/tmp/rv-u2-live/`) | `untrusted` + `workspace-write` | 5 of 5 PASS | 5 of 5, all eight steps PASS |
| `/tmp/p1u2-runs/`, 5 runs | `on-request` + `read-only` | 4 of 5 | 4 of 5 |

Each write asked once, as a `commandExecution` request (`printf … > a.txt`, a heredoc or `python3 -c`). No turn began with the failed sandboxed attempt that the old policy produces. One run also asked for `pwd` before the write, and both were approved. In step 2 every write was declined, `b.txt` stayed missing and the model said so.

**Two things to record.**

- Under `untrusted` the approval offers `[accept, acceptWithExecpolicyAmendment, cancel]`. It has no `decline`. `s2` answers `decline` anyway, and Codex honoured it in all 15 runs (`Completed command declined`). That is a fact about this Codex build, and `codex/PROTOCOL.md` should say so. The daemon (§2.6) runs `on-request` + `workspace-write` and answers Deny with `decline`, so this matters to the drift check only.
- `s2` no longer tests the policy the daemon runs. The old pair didn't either, because `on-request` + `workspace-write` writes in the workspace without asking (`codex/PROTOCOL.md`). That was already the reason for using a different policy.

**Cascade.** With the policy fixed, step 1's miss no longer cascades in practice. To make a miss in any step unable to fail another, two small changes would help. Step 6 could re-answer the ids from steps 1 and 2 together. Step 5 could ask about a reply that needs no tool (the `pong` turns). I would not require them. Each adds code to guard against a failure that the policy change removes.

## The interrupt before the turn starts

**Confirmed from the logs, with one caveat.**

- **Claude, interrupt sent right after `send_user` (step 3d).** In all ten `s1` logs I have (`old/s1-run1..5.log`, `s1-run1..5.log`), the CLI acknowledged the interrupt and then ran the whole turn to `result/success` (`terminal_reason: "completed"`). The committed fixture shows the same. `claude/PROTOCOL.md` says one run in eleven aborted. That eleventh run is not in `/tmp/p1u2-runs/`, so I could not check it. Either way the interrupt is lost at least 10 times in 11, and the acknowledgement does not say which happened.
- **Codex, interrupt sent as soon as `turn/start` answers (step 3d).** All five `s2` runs in `/tmp/p1u2-runs/` and all five of mine got `-32600 no active turn to interrupt`, and the turn ran to `Completed`.
- **Both, interrupt sent on the turn-started event (step 3).** Claude on `system/init` aborted in 10 of 10 (`aborted_streaming`, `text=""`). Codex on `turn/started` gave `interrupted` in 5 of 5 (`/tmp/p1u2-runs/`), with `items=[]`, and step 3 passed in all five of mine.

So the turn-started event is the earliest point at which an interrupt works on both CLIs. The implementer's recommendation holds.

**The rule for §2.5.** A turn has three states, not two, and an interrupt that arrives in the middle one waits for the turn to start:

```rust
enum Turn {
    Idle,
    /// `Send` was accepted; the agent has not reported `TurnStarted` yet.
    Starting(Held),
    Running(NativeTurn),
}

/// What arrived while the turn was starting.
enum Held {
    Nothing,
    Interrupt,
}
```

| Input | `Idle` | `Starting(held)` | `Running(native)` |
|---|---|---|---|
| `Send` | log `UserMessage`; `send_user` / `send_turn`; `Starting(Nothing)`; `Accepted` | `Rejected(TurnInProgress)` | `Rejected(TurnInProgress)` |
| `Interrupt` | `Rejected(NoTurnRunning)` | `Starting(Interrupt)`; `Accepted`; nothing is sent to the agent | `interrupt` / `interrupt(turn)`; `Accepted` |
| `Step::TurnStarted(native)` | ignore | `Running(native)`; if `held` is `Interrupt`, send it now | ignore |
| `Step::TurnEnded(outcome)` | log it | `Idle`; a held interrupt is dropped | `Idle` |

Three changes follow in §2.7.

- `Step::TurnStarted` carries a `NativeTurn` instead of a `TurnId`.
- Claude's `TurnStarted { .. }` row maps to `TurnStarted(NativeTurn::Claude)` instead of "none". This also removes the asymmetry the drift review flagged between the two `TurnStarted` rows.
- Codex's row becomes `TurnStarted(NativeTurn::Codex(turn))`.

A second `Interrupt` while `Starting(Interrupt)` is `Accepted` and changes nothing. If the agent's stream ends while `Starting`, `AgentGone` closes the session as today. The `TurnCompleted { Interrupted }` the user expects still comes from the agent after the held interrupt is sent. Unit 4 needs a gated test for this: `Send`, `Interrupt` before the fixture's `system/init`, then the recording's 3c turn. Unit 5 needs the same for Codex.

## §2.7's const tables

The design's `TOOL_FIELDS` and `CODEX_OUTCOMES` can't be written in v5. Their `&'static str` fields are `type.lifetime`, which 0009 allows only in a library trait impl. I measured whether allowing `'static` in a const table's struct would pay, scoring the lifetime at the tolerated tier it would get.

| Code | Match (score / tokens) | Const table, `'static` tolerated | Change |
|---|---|---|---|
| Tool detail | 170.0 / 189 (fix 1) | 338.0 / 355 | +99% |
| Codex outcomes | 50.0 / 62 | 108.0 / 114 | +116% |

Measured with `tool_detail_one_match.rs`, `tool_detail_table.rs`, `codex_outcome_match.rs` and `codex_outcome_table.rs`. The table scores are the measured ones minus 3.0 per lifetime token (5.0 outside to 2.0 tolerated).

**No proposal.** A string-keyed lookup is shorter as a match on string literals. The match needs no row struct and no `find` closure, and `|` groups keys that share a value. The table form pays only when a row has several fields that more than one caller reads, and neither table here does. Unit 4 should write `codex_outcome` as the match above.

**For the owner.** `docs/subset.md`, quality 7's first form, uses `PROVIDERS.iter().find(|p| p.name == name)` as its example. That can't be written in v5 when `name` is a `&'static str` field. The example should key on something other than a string, or the form should say it is for rows of non-string data.

**Required fix to the design.** In §2.7, replace `TOOL_FIELDS` and `CODEX_OUTCOMES` with the two matches, and say why in one line.

## Friction points

1. **A const table can't hold strings.** Covered above. The match is shorter at any tier, so this is not proposed.
2. **The `cue` or-pattern.** The arm lists `(Plan::Interrupt(Cue::X), Cue::X, None)` once per cue, in two binaries. The alternative needs a comparison outside a predicate closure, or an `if let` with a guard. The arm is 3 lines in each of 2 places, about 20 tokens each. That is too small to clear the 15% bar on either function, and too few points to clear the three-of-one-kind bar. **Not proposed.**
3. **Indexing.** The literal id is clearer than `r.ids[0]` and costs nothing, as the implementer notes. **Not proposed.**

## Proposals

None. The highest proposal number is 0037 on both `main` and `subset-v6`, so the next one would be 0038.

## Weight

No weight change is proposed. The one weight this review touches is `type.lifetime` at tolerated. Moving it, or allowing it in const tables, changes nothing, because the table form costs twice the match in tokens before any weight applies. The weights already rank the two forms in the same order as the token counts (`expr.match` encouraged, `item.const` neutral, the row struct's primitive fields tolerated), so they hide no cost here.

## Advisory, not required

- **`s2` still reads the owner's `~/.codex/hooks.json`** (drift review advisory). The new `untrusted` policy doesn't change that.
- **`s1`'s write steps (1, 2, 3b, 5) depend on haiku calling Write.** They passed in all 15 `s1` runs I have. Claude's CLI has no per-call tool choice. If they ever miss, use the drift review's remedy: retry the turn once when `permissions=[]`.
- **3d's `Expect::Either` in `s1` cannot fail on outcome.** That is right while the CLI does either. If a CLI version starts aborting reliably, the PROTOCOL note should change, and the step will not notice. The detail line prints `finished=`, so a reader can still see it.
