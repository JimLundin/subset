## CodexHub and the shared session

- **Two sessions racing to start the server.** The hub handles one `HubMsg` at a time and awaits `up()` and `start_thread` inside its loop. A second start waits in the inbox until the first has its server and its route, then reuses the same `CodexServer`. No second app-server can start. The live run confirms one `codex app-server started` line for three sessions. The e2e test starts its sessions one after another. It has to, because the fixture gives the first thread to whichever start reaches the hub first.
- **Unknown or closed threads.** An event for a thread with no route is logged at `debug` and dropped. When a session's actor ends, its receiver is dropped, and the next event for that thread fails to send and removes the route. A route whose thread never sends again stays in the map, which costs a few bytes per closed session.
- **Server exit, and restart.** `CodexServer`'s actor fails every pending request with `Exited`, then emits `CodexEvent::Exited`. So a session awaiting `send_turn` or `interrupt` logs `TurnCompleted { Failed }` or an `Error` first, then reads the exit from its feed and logs `SessionClosed { Exited }`. That order is right. The hub drains every route, so even when `try_send` finds a channel full and the exit is lost, dropping the sender ends that session's feed and it closes with "the agent's events ended". **No session can be stranded.** A thread that starts on a dying server gets its route before the hub reads the exit, so the drain reaches it. One narrow race remains. A start that reaches the hub after the process died but before the hub read `Exited` (tokio's `select!` picks at random) uses the old handle and fails. The session closes with `FailedToStart` ("the codex app-server has exited", or a broken pipe), and the next start works. I could not trigger it with the fake, so this is inferred from the code. Advisory: on a start error, set `Server::Down` and retry once. Dropping the old `Up` drops its receiver, so its stale `Exited` can't later close the new server's sessions.
- **Head-of-line blocking.** `route` awaits `send` on a 256-slot channel. One session that doesn't read for 256 events stalls routing for every Codex session. A session only blocks on log appends and on single agent round trips, so I don't see this happening. It is a risk to keep in mind if a session ever awaits something slow.
- **Interrupt by turn id, held.** `Turn::Starting(Held::Interrupt)` sends on `Step::TurnStarted(NativeTurn::Codex(turn))` with that turn's id. The fixture's nested `await` matches `{"method": "turn/interrupt", "params": {"turnId": …}}`, so the test fails if the id is wrong or the interrupt is sent early. The live at-send interrupt was held and sent on `turn/started`.
- **Approve and deny reach the right request.** `CodexThread::respond` answers by `ApprovalId`, which is Codex's server-wide JSON-RPC id, so the thread doesn't matter for the answer. The two-thread fixture waits for `{"id": 0, "result": {"decision": "accept"}}` and `{"id": 1, … "decline"}`. I swapped the two decisions in the fixture, and the test failed after 10.2 s on the step timeout. So the test does catch a crossed answer.
- **The `s2` 3b order.** Codex completes the turn as `Interrupted`, then resolves the request. The session logs `TurnCompleted { Interrupted }`, then `RequestResolved { Withdrawn }` when `ApprovalCancelled` arrives, and the e2e test asserts that order. So **yes, the request is `Open` in the host's state and log between the two events.** The log ends consistent, because Codex always sends the resolve. The command's `ToolCall` is never finished in the host log, because Codex never completes that item. The client's End fold (§12) shows it `Stopped`. Two small gaps follow, and neither is a fix:
  - A `Resolve` landing in that window is `Accepted`. The host logs `Decided` and writes an answer that Codex ignores, so the log says "approved" for a command that never ran. The window is the time between two adjacent stdout lines.
  - If the server exits inside the window, the request stays `Open` in the log for good, behind `TurnCompleted` and `SessionClosed`.

  One rule closes both. On `Step::TurnEnded`, withdraw every request still open. Codex's later `ApprovalCancelled` then finds nothing, and the e2e test's event list is unchanged. I estimate it at about 50 tokens. It is advisory, because the client already folds these states.

## The impossible-combination arms

`interrupt` and `answer` each have an arm for an `Agent` of one provider with a `NativeTurn` or `NativeRequest` of the other. Within v7 there is no way to rule these out that is no larger:

- **Per-provider state in one enum.** The arms exist because `Turn` and `Pending` are shared while their payloads are per provider. Without generics, moving them into `Agent::Claude { .. } | Agent::Codex { .. }` needs a `ClaudeTurn` and a `CodexTurn`, plus a `Pending` and a request map per provider. `order` (324 tokens) and `resolve` (220) then run once per provider, or through a projection that is itself new code. By my estimate, the two arms cost about 70 tokens and the two native enums about 80. The redesign is several hundred tokens larger (estimated, not written out), so it is not required.
- **Handles inside the native ids** (`NativeRequest::Codex(CodexThread, ApprovalId)`). This removes the pairing, but `Step` loses `PartialEq`, which the mapping tests and `withdraw` need, and pure mapping would carry handles. It is rejected.
- **`agents` tracking the active turn**, so that `CodexThread::interrupt()` takes no id. This removes `NativeTurn` and the interrupt arm, but it puts the turn in two actors and reverses §11's "Codex interrupts by turn id". It is a design change, not a fix.

The same check found one illegal combination that *can* go for free. `Agent` and `Feed` are two parallel enums, so `Agent::Claude` beside `Feed::Codex` can be represented. That is fix 1.

## Required fixes

All are in `required-fixes.diff`, formatted with `rustfmt`.

1. **`Agent` holds its feed** (`session.rs`). `Agent::Claude { session, events } | Agent::Codex { thread, events }`, with `Agent::next` in place of `Feed::next`. `start` returns `Agent` rather than a pair. This removes the `Feed` enum and the representable mismatch between the two enums. It is the brief's standard for focus 2: no larger. **Measured:** score 2,684.0 to 2,677.0 (-7.0), tokens 2,926 to 2,933 (+7).
2. **`route` acts on a failed send with `if let`** (`codex_hub.rs`). `match … { Ok(()) => {} Err(_) => { … } }` is the empty-arm `match` that 0027 replaced (`examples.md` §21). The v7 form exists, and clippy accepts it: `if let Err(mpsc::error::SendError(_)) = route.send(event).await { … }`. It names the payload's tuple-struct pattern, as 0027 prescribes for `Some(Open { .. })`. This is a one-way fix (quality 6), and it costs score. **Measured:** 1,020.0 to 1,047.0 (+27.0), tokens 1,093 to 1,094. The `if let` is tolerated (2.0) and the `match` it replaces is encouraged (0.5). One site is not enough evidence for a weight proposal, but it shows the required form scoring worse than the form it replaced.
3. **One arm for `ApprovalRequested`** (`mapping.rs`). Three arms shared the shape `codex_open(id, item, <tool>)` and differed only in the tool. `approval_tool(kind) -> Option<ToolKind>` maps each kind to its tool, with `None` for a question, and one arm opens the request or emits the question error. `codex_open` goes. This is quality 7's second form. The fix also imports the module for F5 (below), so `codex::TurnOutcome` and `codex::Decision` replace the full paths, as §2.7 writes them. **Measured, mapping code without tests:** 1,436.0 to 1,397.5 (-38.5), tokens 1,767 to 1,713 (-54). `codex_thread_steps` with `codex_open` goes from 459.0 to 426.5 with `approval_tool`.
4. **One mapping table for both providers, keeping only what the e2e tests can't reach** (`mapping.rs` tests). This follows unit 4's fix 2. The e2e tests already pin Codex `TurnStarted`, a command `Item` started, an approval for a command, the `declined` status and `Completed` and `Interrupted` turns, all through real stdout. Three Codex cases remain: a file-change item's paths, a question, and a `Failed` turn with no message. They join the five Claude cases in one table of `Case { got, want }`, with one `unzip` and one `assert_eq!`. The second struct and the second assertion go. **Measured:** the tests go from 1,316 tokens to 968 (-348). The whole file goes from a score of 2,728.5 to 2,353.5 (-13.7%) with fix 3.
5. **One body for the two held-interrupt tests** (`e2e.rs`). `an_interrupt_before_the_turn_starts_is_held_until_it_does` and `a_codex_interrupt_before_the_turn_starts_is_sent_by_turn_id` were the same 20 lines, differing in the host, the directory and the provider (quality 7). `held_interrupt(fx, dir, provider)` holds the body, and each test is a two-line call. **Measured:** 8,547.0 to 8,391.5 (-155.5), tokens 8,168 to 8,030 (-138).

## Fixtures and the fake CLI

- **The nested `await` match is right.** `has` recurses through dicts and compares everything else for equality, so `{"result": {}}` matches any result. An answer's `await` names both `id` and `result`, which keeps it from matching one of our own requests with the same id. The `awaited` flag survives fake lines, such as a `release`, and resets after the next real line, so it applies to exactly the `serverRequest/resolved` that follows.
- **No test can hang forever.** Every read of the link's updates goes through `next`, which has the 10 s `STEP` timeout. Without the 5 s fallback, a resolve with no answer now waits as long as the test lets it. The swapped-decision probe above shows that the test then fails after 10.2 s. Commands are bounded too. A command waits at most for one agent round trip, and `agents` times those out at 120 s (`REQUEST_TIMEOUT`, which covers `initialize`, `thread/start`, `turn/start` and `turn/interrupt`). `respond` doesn't wait for Codex. So the worst case is a 120 s failure, not a hang. `codex_replay.rs`, which plays `server1.jsonl` through the same fake, still passes. Its resolves all follow answers, and its reads time out at 20 s.
- **`build-codex.py` reproduces all five recordings byte for byte.** I ran it on a copy of `fixtures/` and compared with `cmp`: `codex-two-threads`, `codex-interrupt`, `codex-held-interrupt`, `codex-withdraw` and `codex-exit` are identical.

## The app

The screenshots in `docs/p1/screens/` show the Codex flow working: the approval card with the command, "Approved by browser" and the finished turn, on desktop and on the phone. Two things for the owner, flagged and not designed:

- **Codex rarely asks.** Under `OnRequest` with `WorkspaceWrite`, Codex edits and runs commands inside the session's directory without asking. The live check has to tell it to escalate before it asks at all. A user coming from Claude's `Default` mode would expect a prompt before a write and get none. Nothing in the New Session screen or the session header says what a Codex session may do unasked.
- **The approval card drops Codex's reason.** `ApprovalKind::Command` carries `reason`, such as "needs escalated permission to write outside the workspace", and `mapping` discards it. When Codex does ask, the reason is what makes the request rare and worth reading. The phone screenshot also shows no provider badge in the session header, where the desktop shows "Codex, running".
