## Required fixes

1. **A row struct must be used only as a table's row.** `table.rs` treats a struct as a row when any `const` holds it as `&[Row]` and no struct literal of it stands outside *any* `const`. So `const CONFIG: Row = Row { host: "example.com", path: "/api" };` beside an empty `const UNUSED: &[Row] = &[];` passes, and `Row` becomes a record of string constants that is never scanned. A fn-local `const` does the same, and `fn one() -> Row { ONE }` carries the row out through a signature. Count a struct literal as a table build only inside the initializer of a `const` whose type is `&[Row]`, `[Row; N]` or `&[Row; N]`, and drop row status when any other `const` has the type `Row`. Key the structs by their module path, or drop row status when two structs in the file share a name: today `mod elsewhere { struct Row { label: &'static str } }` passes because a `Row` in another module has a table.
2. **The keyed lookup misses the forms around `==`.** Flag the closure when any operand of `&&` or `||`, the operand of `!` (for `!=`), or the tail of a block body is a keyed comparison. Add `any` to `LOOKUPS`. See through `enumerate`, `skip`, `take` and `filter` between the table and the lookup, and bind the row from `(_, row)` and from a struct pattern (`Row { name: n, .. }`). Treat `PartialEq::eq(a, b)` and `a.cmp(b).is_eq()` as `==`. Follow a `let` binding of the table within the fn. Give a table whose element type is `&str` a key for the element itself, so `NAMES.iter().position(|n| n == &name)` is flagged. Failing inputs are the "passes" rows of the keyed-lookup table above.
3. **The range rule has three ways round it.** (a) `bytes.get(RangeInclusive::new(1, 2).into_iter())` passes, because `into_iter` marks its receiver as iterated and returns the same range. Leave `into_iter` out of `iterates` for a receiver that is a range built by name. It is a no-op there anyway. (b) `let low = Bound::Included(1); let high = Bound::Excluded(3); bytes.get((low, high))` passes, because `bound` reads only the tuple's own elements. The subset has no use for a `Bound` value, so flag `Bound::Included`, `Bound::Excluded` and `Bound::Unbounded` wherever they are built. (c) `bytes.get(RangeFull::default())` and `bytes.get(Range::<usize>::default())` pass, because only `new` is matched. Match any associated fn whose type segment is in `RANGE_TYPES`.
4. **Nested pairs carry a third field.** `Vec::from([(input, (Touch::None, name)), ..])` passes the tuple-table rule. Count a row's fields through nested tuples, so `(a, (b, c))` has three.
5. **A doc comment moved.** In `shape.rs` the new items were inserted between `/// Methods that compare by name, as a.eq(&b) (proposal 0040).` and `COMPARE_METHODS`. That line now sits on top of `RANGE_TYPES`, which carries two doc comments, and `COMPARE_METHODS` has none. Move it back.
6. **The docs follow the fixes.** After 1 to 4, update the README's "0042's tables are read from one file" and "A range built by name" entries and `compromises.md`'s "What a table is" to the forms left to review: a helper fn, a `map` projection before the lookup, and near-equalities such as `eq_ignore_ascii_case`. Example 27 says `&'static str` in a tuple row is flagged. That holds only for a spelled `'static`: `const PAIRS: &[(&str, Kind)]` passes and is scanned, as it was under version 7. Say so, or ask the owner whether an elided tuple row should go the way of the spelled one.

## Broader than ruled

**The tuple-table rule.** The owner ruled on test tables. The branch flags any array literal with a tuple of three or more fields, anywhere, and `docs/subset.md` states the ruling in that wider form ("a test case table included"). In practice the extra reach is small. A `const` table, or an array passed to a fn of ours, already needs a named struct under 0001, because it outlives its expression or crosses a signature. What remains is a short-lived array passed straight to a library call, for example `client.send_all([("a", 1, Kind::A)])`. That one-element array is flagged though it is not a table. `crates/` has no such site, and arrays of three-field tuples are rare in library APIs. Either have the owner confirm the wider reading in `subset.md`, or require two or more rows, or restrict the check to test code.

**The range rule.** Ranking from most to least likely to bite:

- `RangeInclusive::new(first, last).contains(&port)` is flagged. It is a membership test, not an index, and the subset has no other total form for it besides a match guard or two comparisons in a predicate.
- `let ports = RangeInclusive::new(first, last); ports.rev().collect()` and a range stored in a field, `Ports { range: RangeInclusive::new(first, last) }`, are flagged. `compromises.md` records this as stricter than needed. The fix is cheap, since storing `first` and `last` and building the range where it is iterated is what `rtc.rs`'s `PortRange` does already.
- `std::iter::zip(RangeInclusive::new(1, 100), names)` and `Iterator::zip(RangeInclusive::new(1, 100), names)` are flagged, while the method form `.zip(..)` passes.

None of these appears in `crates/`, so none blocks the branch. The `contains` case is the one I would allow, by adding `contains` to the methods that may take a range built by name.

**0042.** Nothing broader. Flagging `Option<&'static str>`, a tuple field and an array field inside a row struct matches the owner's "only as a field type", read strictly.
