# String fields in a `const` table that is scanned in order

## Rule
A struct used only as the row type of a `const` table may have
`&'static str` fields, when the table is read by scanning its rows in order
with one predicate that tests the input against a field (`find`,
`position`), as in `user_agent.contains(row.marker)`. A lookup keyed by
equality on a string stays a `match` (quality 7, `p1-u2.md`). No other
lifetime is allowed, and a `&'static str` never appears in a signature.

## Before
`crates/client/src/device.rs` at `3a61161`. It has a `Device` enum, a
`const DEVICES: &[Device]` that fixes the scan order, and two `match`es
over the seven variants, `marker()` and `name()`. A third `match` turns a
Mac with a touchscreen into an iPad.

## After
`docs/subset/measurements/p1-smoke-fixes/device-table.patch`:

```rust
/// A word in a user agent, and the device it names without and with a
/// touchscreen.
struct Row {
    marker: &'static str,
    name: &'static str,
    touch_name: &'static str,
}

/// Checked in this order: an iPhone's or iPad's user agent also says "Mac
/// OS X", and Android's and ChromeOS's also say "Linux".
const DEVICES: &[Row] = &[
    Row { marker: "iPhone", name: "iPhone", touch_name: "iPhone" },
    // ..five more rows..
    Row { marker: "Macintosh", name: "Mac", touch_name: "iPad" },
    Row { marker: "Linux", name: "Linux", touch_name: "Linux" },
];

pub fn device_name(user_agent: &str, touch: Touch) -> ClientName {
    let name = DEVICES
        .iter()
        .find(|row| user_agent.contains(row.marker))
        .map_or("Browser", |row| match touch {
            Touch::None => row.name,
            Touch::Screen => row.touch_name,
        });
    ClientName(String::from(name))
}
```

The branch's ten-case test passes unchanged against it.

## Weight
tolerated. This is the weight `type.lifetime` already has, and the rule
admits only `'static` on a string.
Boundary use: doesn't apply. No library fixes the shape.

## Qualities
1. Named states: kept. `Device` goes away, but no code branched on it.
   The only rule that read it, a Mac with a touchscreen is an iPad, becomes
   the `touch_name` column. The output was a string on the wire already.
2. Visible branching: kept. The one remaining decision, touch or not, is a
   `match`.
3. Forward data flow: kept.
4. Errors are values: kept. A user agent that names no device is still the
   `map_or` default.
5. Local reasoning: kept, better. A row says everything about one device,
   where before a reader joined `DEVICES`, `marker()` and `name()` by
   variant.
6. One way: kept if the rule stays narrow. A keyed lookup is a `match`, and
   an ordered scan is a table. The checker can't tell them apart, so review
   enforces it, the same way it enforces quality 7's forms today.
7. Repetition is data: kept, better. The seven devices are one table where
   they were one list and two matches.
