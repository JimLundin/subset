# `true`/`false` for external `bool` parameters

## Rule
A `true`/`false` literal is allowed only as a direct argument to a function or method from outside our crates whose declared parameter type is `bool`, or as the value of a `bool`/`Option<bool>` field of a struct from outside our crates. Examples are `OpenOptions::create(true)`, `Command::kill_on_drop(true)`, `RtcDataChannelInit::set_ordered(true)` and `InitializeCapabilities { experimental_api: Some(true), .. }`. A generic parameter that we fill with `bool` (`watch::channel(false)`) does not qualify. Our own types never hold a `bool` (§C1).

## Before
No subset-only form exists. These APIs take a `bool`, and the only way to write a `bool` value without the literal is a computed expression standing in for a constant.

## After
```rust
// crates/daemon/src/lib.rs
std::fs::OpenOptions::new()
    .write(true)
    .create_new(true)
    .mode(0o600)
    .open(path)
```

Friction points removed: 11 of the 48 `expr.lit.bool` sites fit the rule. 5 are `AtomicBool` calls in `crates/daemon/src/rtc.rs`, which go with the interior-mutability gap in the review. The other 32 build or compare our own `bool` values and are rejected with `type.bool` (§C1).

## Qualities
1. Named states: kept. The `bool` belongs to the library's API and never enters our types.
2. Visible branching: kept. A literal argument is not a decision.
3. Forward data flow: kept.
4. Errors are values: kept.
5. Local reasoning: kept. The method name says what the flag means (`create_new(true)`).
6. One way: kept.
