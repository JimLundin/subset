# A match guard that compares two values

## Rule
A `match` arm may have a guard whose body is one comparison (`==`, `!=`,
`<`, `<=`, `>`, `>=`) or one `matches!`, with no `&&`, `||` or `!`. Use it
when the arm depends on a value its pattern bound being equal to, or
ordered against, another runtime value. A later arm must cover the same
pattern without the guard, so the "otherwise" case is written out.

With the guard, choosing an arm by comparing two runtime values has one
form. Two older forms go:

- `a.eq(b).then_some(x)`, which bootstrap review §A4 sanctioned because no
  predicate existed then;
- `Some(x).filter(|x| ..)` on an `Option` built only to ask one question.

`filter` and the other predicate adapters keep their 0028 role. They select
from a collection or an `Option` that already exists.

This reopens two earlier rulings. 0028 lists "a `match` guard" among the
places a boolean stays out, and bootstrap review §A3 rewrites guards as a
nested `match` on the guarded value. §A3 works when the guard compares
against a literal or a variant. It can't express equality of two runtime
values, because a pattern can't name a runtime value. That gap is why §A4
added `.eq(..).then_some(..)`. Unit 3 shows four sites of this kind in one
change, written in both older forms.

## Qualities
1. Named states: kept. The comparison reads two named values, and its
   `bool` never becomes a binding, a field or a return value.
2. Visible branching: kept. Each arm is written out. The rule requires an
   unguarded arm for the same pattern after the guarded one, so the "not
   equal" case is a visible arm, as the `None` arm is today. Rust's
   exhaustiveness check ignores guards, which is why the rule writes the
   fallback out instead of trusting `_`.
3. Forward data flow: kept.
4. Errors are values: kept. `authenticate` still returns the refusal as an
   `Err` value.
5. Local reasoning: kept, and helped. The condition sits on the arm it
   selects. Today it sits in an `Option` built inside the arm's body.
6. One way: kept, and helped. This diff spells one equality two ways
   (§A4's `.eq(..).then_some(..)` in `host_view.rs` and 0028's
   `Some(x).filter(..)` in `serve.rs`). Both are allowed in v6, and neither
   is the stated form. After this proposal, the guard is the one form.
7. Repetition is data: kept.

## Tool change
`tools/subset` allows `expr.match.guard` when its expression is one
comparison or one `matches!`, and allows that comparison as it allows a
predicate body. It flags `PartialEq::eq` and `ne` called by name outside a
predicate closure. It also flags `Some(<expr>).filter(..)` where the
`Option` is built at the call. A guarded arm with no later arm for the same
pattern is a review check. `bootstrap-review.md` §A4's last sentence then
points to this proposal.

## Owner decision (2026-11-12)

Accepted, with one amendment. The lift `Some(x).filter(|x| ..)` (and
`.then_some(..)` on a library `bool`) stays allowed when the predicate
combines library booleans with `&&`, `||` or `!`, since the guard allows only
one comparison and such a check would otherwise have no allowed form (for
example the composer's Enter-key check, `docs/subset/reviews/p1-u6.md`). Only
the single-comparison lift is replaced by the guard.

Clarifications (2026-11-12, from the v7 review, `docs/subset/reviews/v7.md`):

- A `filter` of one comparison on an `Option` that already exists, whose
  result is matched at once (a `match` or `if let` scrutinee), is a lift
  too, and is written as a guard. A `filter` whose result is kept or passed
  on stays allowed.
- `Some(x).filter(..)` that combines comparisons with `&&` or `||` stays
  allowed. A guard can't hold it, so the lift is the only form available.
- A guard tests a value its arm's pattern bound. A guard that compares with
  a literal, a variant or a constant, or a `matches!` on a place, is a
  pattern and is written in the arm (bootstrap review §A3, §A4). Two
  equalities in one arm are one guard over a tuple, as in `seen == (a, b)`
  with `seen` bound; equality is never `cmp` against `Ordering::Equal`.
- `matches!`, in a guard or a predicate closure, takes a place or a call and
  a pattern with no `if` and no `true` / `false`.
