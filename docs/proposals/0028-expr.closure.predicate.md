# Predicate closures

## Rule
A closure passed directly as the argument of a filtering adapter (`filter`, `find`, `any`, `all`, `position`, `take_while`, `skip_while` or `retain`) may have a **boolean expression** as its body. A boolean expression is `matches!(..)`, a comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`), or `&&`, `||` and `!` over boolean expressions.

Plain boolean values stay out:

- `true` and `false` literals, except under 0023's library boundary rule, as before. A predicate closure can't return `true`.
- `bool` bindings, fields, parameters and return types of our own.
- Boolean expressions anywhere outside such a closure: in a `let`, an `if let` condition, a `match` guard, an argument or a return value.

The counting idiom is `iter.filter(|x| matches!(x, Variant)).count()`. `filter_map(.. Some(()) ..).count()` and a `fold` that only counts are no longer the idiom.

In the owner's words: "anything that filters like a conditional is acceptable. I don't want plain boolean values."

## Before
The counting forms 0025 found in `crates/agents`, each written to get past a lint or the missing `filter`:

```rust
// bin/s1.rs:540 and bin/s2.rs:593
.fold(0_usize, |failed, verdict| match verdict {
    Verdict::Pass => failed,
    Verdict::Fail => failed.saturating_add(1),
});

// tests/replay.rs:216-222
let results = recording
    .lines()
    .map(|line| match frame_type(line).as_deref() {
        Some("result") => 1,
        _ => 0,
    })
    .sum::<usize>();
```

## After
```rust
.filter(|verdict| matches!(verdict, Verdict::Fail))
.count();

let results = recording
    .lines()
    .filter(|line| matches!(frame_type(line).as_deref(), Some("result")))
    .count();
```

## Measurements
Not measured as a proposal of its own. The owner decided it from the counting rows of 0025 (`unnecessary_filter_map`, three sites, -4.2% for the `filter_map` form) and the agents review's equality rows. The `filter` form is shorter than the `filter_map` form at each site, since the `match` and its `None` arm go.

## Qualities
1. Named states: kept. A predicate reads a state through `matches!` with a named variant, and its `bool` never leaves the adapter call.
2. Visible branching: bent, and confined. A comparison or `matches!` is a decision that isn't a `match`. It is allowed only where the adapter itself is the branch: the item is kept, found or counted.
3. Forward data flow: kept.
4. Errors are values: kept.
5. Local reasoning: kept. The predicate is written at the call.
6. One way: kept. Selecting is `filter`, counting is `filter(..).count()`, transforming is `filter_map` with a `match` (`examples.md` §8 and §22).

## Tool change
`tools/subset` allows `macro.matches`, the eight comparison and logical operators and `!` only in the boolean tree of a closure passed straight to one of the listed methods. Operands of a comparison are ordinary expressions, so an operator nested inside one (`f(a == b) == c`) is flagged. `filter_map(..).count()` is flagged. A `fold` or `map(..).sum()` that only counts can't be told from a real total in the syntax, so it is a review check.
